Contributing

The project is a small Python service, a browser UI and three agents that all speak one reading schema. This chapter explains where things live, how to run the tests, how to add a node type, and what a pull request has to contain before it is reviewed.

v0.1~11 min read

Contributions are expected to keep the deployment story intact: one server, one SQLite file, no cloud dependency and no build step in the documentation. If a change needs a new daemon, a message broker or an external service to work, it is the wrong shape for this repository.

Repository layout

wifi-survey/
├── server/          FastAPI app, API v1, SQLite schema, static viewer
│   ├── wifisurvey/  package: config, auth, db, main, model_import, cli
│   ├── static/      index.html, app.js, style.css, vendored three.js
│   └── tests/       pytest suite against a temporary database
├── modelkit/        geometry pipeline: floors, walls, regularisation, plans
├── agent-linux/     stdlib Python agent, systemd user unit, tests
├── agent-android/   Termux script (termux-wifi-scaninfo)
├── agent-esp32/     Arduino sketch (PlatformIO project)
├── installer/       install.sh, uninstall.sh, unit template, Dockerfile, compose
├── docs/            the documentation site published by GitHub Pages
├── scripts/         scrub_check.py and maintenance helpers
└── tests/           cross-cutting fixtures and end-to-end scenarios

The split is by runtime, not by layer. server/ owns HTTP, authentication and persistence, and serves the viewer from the same origin. modelkit/ is computation over meshes and polygons with no database handle and no network access, which is what makes it testable without an instance. agent-*/ contains one directory per platform; the shared contract is the JSON payload, not a library. Heatmap, propagation, position and tuning code will land in server/ as separate modules when those phases are built.

If you are unsure where a change belongs, ask whether it needs a request context. Anything that does belongs in server/; anything that could run in a script with a mesh and two arrays belongs in modelkit/.

How the pieces connect

One process serves the UI and the API on port 8800. Agents post readings into it, the engine computes from stored rows, and the browser reads results over the same origin. The database is the only shared state.

Two consequences follow from that picture, and both matter when you write code. First, an agent never talks to the engine directly; it posts a reading and the server decides where it lands. Second, the engine cannot fetch anything it was not handed, so every function takes its inputs explicitly — that is why it can be unit-tested with a dictionary of points and no running service.

Schema is the contract

The reading payload — node_id, ts, position with x, y and floor, and a samples array of bssid, ssid, band, channel, freq_mhz and rssi — is version 1 and shared by every node type. Changing it is an API change, not an implementation detail.

Development setup

Use a virtual environment; the installer is not involved in development and should not be run against a working checkout. The version of Python is pinned in pyproject.toml, and the editable install pulls in the test and lint extras.

git clone https://github.com/jpullen724-stack/wifi-survey.git
cd wifi-survey/server
python3 -m venv .venv
. .venv/bin/activate
pip install -e '.[dev]'

Then check that the tree is healthy before you change anything, so that a later failure is clearly yours:

cd server && python -m pytest
cd ../modelkit && python -m pytest
cd ../agent-linux && python3 -m unittest discover
cd .. && ruff check
python3 scripts/scrub_check.py

Running the server locally works without the installer; point it at a writable data directory so you never touch /var/lib/wifisurvey on a machine that already has a real survey. wifi-survey init --data-dir /tmp/ws-dev writes a config with fresh secrets, then wifi-survey serve runs it on a port you choose. A local run on another port keeps the mDNS name out of the way and avoids collisions with an installed instance.

Test strategy

Tests are built around isolation rather than mocks of the framework. Each test gets its own application instance and a temporary SQLite file, created and torn down by a fixture, so no test can see another test's readings and the suite can run in any order or in parallel. Nothing binds a real port unless the test is specifically about the listener, and nothing reaches the network.

Agents are exercised through a fake agent fixture that emits a deterministic sequence of readings, including the awkward cases: a scan with one BSSID, a scan with a missing SSID, samples from two bands in the same reading, and a timestamp that arrives out of order. The same fixture feeds the API tests, which means the ingest path and the storage path are tested against identical input.

Golden models live in tests/fixtures. They are small meshes with known geometry, used to pin down floor detection and wall extraction: if a change alters which walls are found, the test fails with a readable diff rather than a silently different heatmap. When a change is deliberately supposed to alter that output, regenerate the golden file, review the diff line by line, and commit both together — never regenerate to make a red test green without reading it.

What is not covered: radio behaviour itself. A test cannot assert that your APs are where you say they are, so the suite checks arithmetic and plumbing, and the documentation is explicit about the physical uncertainty that remains.

Adding a node type

A node type is a producer of readings plus a small amount of metadata about what it can do. The engine does not know or care which platform produced a row, so the work is mostly at the edges.

  1. Implement the reading schema Build the version 1 payload exactly: node_id, an RFC 3339 ts, a position object with x, y and floor, and a samples array whose entries carry bssid, ssid, band, channel, freq_mhz and rssi. Do not add fields; if the platform has extra information, put it in the capability metadata instead.
  2. Post it to /api/v1/readings with a node token Authenticate with the token issued at pairing, not with the dashboard token. A node token can post only for its own node id, so a bug that mixes up ids fails loudly with a 403 rather than quietly corrupting a survey.
  3. Add a pairing kind The node claims a six-digit single-use code within 10 minutes via POST /api/v1/pair with code, node_id and node_type. Register the platform so the UI can show the right instructions and so the issued token is scoped to the capabilities you declare.
  4. Declare capability flags Say which bands the device can see, whether it can sample continuously or only on demand, whether it has a usable position source, and whether it reports dBm directly or a percentage that needs converting. The UI hides views a node cannot feed, and the survey page warns before you plan a 5 GHz walk with a 2.4 GHz-only node.
  5. Publish accuracy metadata Record the conversion used, its error margin and any known throttling. If the platform reports a percentage, state the formula; the Linux agent uses -100 + 0.6 × pct clipped at −40 dBm and is only accurate to about ±3 dB, and a new node should be equally explicit.
  6. Document it Add a section to Scanner nodes covering setup, what it measures, and what it cannot do. A node type that is not on that page does not exist as far as users are concerned.

No plugin API yet

Node types live in-tree under agent-linux/, agent-android/ and agent-esp32/. There is no plugin loader, no sandbox and no stability promise for third-party agents in v0.1, so a new platform is a pull request rather than a package you publish separately. That also means no runtime dependency can be added just to support one node.

Code style and API rules

Ruff runs with the repository defaults; there is no separate formatting discussion, and a pull request that reformats unrelated lines will be asked to narrow its diff. Type hints are expected on public functions in server/ and engine/, since the schema crosses both. New runtime dependencies need a conversation in an issue before the pull request: the installer has to work on four distributions and in a container, and every dependency is another way for that to break.

API versioning is additive within a major version. Adding an optional field or a new endpoint is fine. Renaming a field, changing a unit, or making an optional field required is a breaking change and belongs in a new /api/v2 prefix, with v1 kept working until a release note says otherwise. The reading schema is the strictest case: agents in the field cannot be upgraded on your schedule, so v1 payloads must keep parsing for as long as v1 exists.

Errors are JSON with a stable code and a human-readable message; do not return bare strings, and do not leak a stack trace to a client. Log lines are for operators, so include the node id or survey id and leave the prose out.

Documentation rules

This site is hand-written HTML with one stylesheet and one script. There is no Markdown pipeline, no template engine and no build step, which is deliberate: the pages work from a USB stick and from any static host. Use only the classes documented at the top of assets/style.css, wrap every table in <div class="table-wrap">, and keep code inside <pre><code> with the angle brackets escaped.

Before you push a docs change, run all three scripts from the site directory:

python3 scripts/build_search_index.py
python3 scripts/check_links.py
python3 scripts/check_html.py .

The first regenerates the search index, the second fails on a broken relative link, a missing anchor or an orphaned page, and the third checks tag balance and required head metadata. All three exit non-zero, so they can gate CI. Do not hand-edit search-index.json; it is generated. Do not add images, web fonts or a CDN reference — diagrams are inline SVG, and screenshots are placeholders until real captures exist. Write in neutral English, second person, and put unsupported behaviour in a .callout.limit block instead of softening it.

Pull request checklist

  • The change does one thing, and the description says what problem it solves.
  • pytest, ruff check and mypy server pass locally.
  • New behaviour has a test; a fixed bug has a test that failed before the fix.
  • Schema or API changes are additive, or they are versioned and documented as breaking.
  • No new runtime dependency, or an issue comment agreeing to one.
  • Log lines carry ids, not prose; error responses carry a stable code.
  • If user-visible, the relevant docs page is updated and all three scripts pass.
  • Golden fixtures are regenerated only with a reviewed diff.
  • No secrets, tokens, private hostnames or real survey data in the diff.

Small pull requests get reviewed faster than complete ones. If you are planning something structural — a new interpolation method, a different storage layout, a second listener — open an issue with the design first and save yourself a rewrite.
