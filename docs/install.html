Install

Wi-Fi Survey installs as one systemd service on a Linux host that sits on the same LAN as your access points. The installer creates an isolated Python environment, a service account, a config file and a SQLite database, then prints the URL and the access token you need for the first login.

v0.1~9 min read

What you need

The server does the arithmetic and stores the readings; it needs no Wi-Fi adapter of its own. A mini PC, an old laptop or a small VM is enough. You need root on that machine and LAN reachability from the devices you survey with.

RequirementMinimumNotes
Operating systemDebian 12, Ubuntu 22.04, Fedora 39, ArchAny systemd distribution with a recent Python usually works; these four are the ones tested for each release.
Python3.11 or newerThe installer builds a virtual environment under /opt/wifi-survey and leaves the system Python packages alone.
CPU and RAM1 vCPU, 1 GBKriging a 10 m by 10 m floor at 25 cm resolution is the heaviest job and finishes in a few seconds.
Disk500 MB freePlus roughly 5–20 MB per imported 3D model and a few megabytes per survey.
Init systemsystemdUsed for the unit, the unprivileged service account and log collection.
NetworkOne open TCP port8800 by default, reachable from the LAN. Outbound access is needed during install, not afterwards.
BrowserCurrent Firefox, Chrome, Safari or EdgeWebGL is required for the 3D floor plan view.

No GPU, cloud account, DNS record, TLS certificate or container runtime is required. To run it as a container instead, skip to Docker.

Run the installer

Clone the repository, read the script — it is a few hundred lines of shell and worth ten minutes of your time — then run it as root. The script checks for Python, creates the service account, writes the unit and takes the token from a fresh random seed.

git clone https://github.com/jpullen724-stack/wifi-survey.git
cd wifi-survey
less installer/install.sh
sudo installer/install.sh

An empty prompt is fine on a first install: press Enter to accept the default port and mDNS name. Everything the script asks can also be set as a flag:

FlagDefaultWhat it changes
--port N8800HTTP port for the UI and the REST API. Pick something free if 8800 is taken.
--host H0.0.0.0Bind address. Use 127.0.0.1 when a reverse proxy on the same host is the only client.
--hostname NAMEsurveymDNS name, so the server answers as NAME.local. Use lowercase letters, digits and hyphens.
--no-mdnsmDNS onSkips the avahi record and the /etc/avahi/hosts alias. Use it on hosts where avahi is absent or managed elsewhere.
--data-dir PATH/var/lib/wifisurveyMoves survey.db and models/, for example onto a larger volume.
--config PATH/etc/wifisurvey/config.tomlConfig file location. A user install outside systemd can keep it under $XDG_CONFIG_HOME/wifisurvey/config.toml instead.
--non-interactiveoffAccepts every default and never prompts. Useful in provisioning scripts; combine it with the flags above.

The script is idempotent: running it again on an installed host repairs the unit and the virtual environment instead of creating a second copy. It never overwrites an existing config, token or database.

What the installer creates

PathPurpose
/opt/wifi-surveyApplication code, the Python virtual environment and the wifi-survey command line entry point.
/etc/wifisurvey/config.tomlHost, port, data directory, viewer token, pairing secret and UniFi settings. Mode 0640, owned by root and readable by the wifisurvey group. Read once at startup.
/var/lib/wifisurvey/survey.dbSQLite database in WAL mode: models, floors, APs, nodes, readings and pairing codes.
/var/lib/wifisurvey/models/Imported and converted 3D models, one directory per model.
/etc/systemd/system/wifi-survey.serviceThe unit that runs the FastAPI server as the wifisurvey user.
user wifisurveyUnprivileged system account. It owns the data directory and nothing else.

Backups are a copy of survey.db plus models/. There is no second database, no cache to rebuild and no migration tool to run by hand.

Port and name

After a successful install the unit is enabled and started. Open http://survey.local:8800 if avahi is running on your network, or http://<SERVER_IP>:8800 if it is not. The token printed at the end of the install is the [security] viewer_token in /etc/wifisurvey/config.toml; the UI asks for it once and keeps it in the browser's localStorage.

Check the service before you troubleshoot anything else:

systemctl status wifi-survey
ss -ltnp | grep 8800          # confirm the listener and the bound address
journalctl -u wifi-survey -n 50 --no-pager

To change the port or the name later, edit /etc/wifisurvey/config.toml, then sudo systemctl restart wifi-survey. The mDNS name is published through avahi, so a renamed host needs sudo systemctl restart avahi-daemon as well.

Save the token now

The token is shown once and lives in config.toml, not in the database. Put it in your password manager before you close the terminal: the UI keeps it per browser, so every new browser asks for it again.

Firewall. Allow TCP 8800 from your LAN only. If you rely on survey.local, also allow UDP 5353 for mDNS — blocking it leaves the IP address working and the name silently broken. With firewalld the rule is firewall-cmd --add-port=8800/tcp --permanent followed by a reload.

Known limitation

The server installer targets Linux with systemd. Windows and macOS hosts, and distributions that use another init system, are not supported in v0.1 — the unit file and the service account are part of the install. There is also no published container image: build it locally from installer/Dockerfile. The scanner agents have their own limits, listed in Scanner nodes.

Pair your first scanner

A fresh install has no nodes, so nothing can post readings yet. Pairing takes one command on the server and one on the device that will scan; the JSON it posts is documented in Scanner nodes.

  1. Start the agent on the scanning machine

    On a Linux laptop run agent-linux/install.sh: it copies one stdlib-only Python file, pairs it and can install a systemd user unit. There is nothing to pip install. On Android use the Termux script instead. Nothing listens on the node; it only posts outbound, plus a status page on 127.0.0.1:8790.

  2. Ask the server for a pairing code

    Run sudo -u wifisurvey -H /opt/wifi-survey/venv/bin/wifi-survey pair on the server. You get a six-digit single-use code and the claim endpoint to call. The code expires after ten minutes.

  3. Claim the code from the node

    The agent calls POST /api/v1/pair with {"code","node_id","node_type"}. The server answers with a per-node token; the code is burned on first successful use, so a second attempt with the same code is rejected.

  4. Confirm the node is posting

    The node appears under Nodes with a green heartbeat and its last reading timestamp. Take one sample and watch the count increase before you start walking.

Do not expose this to the internet

The access token is the only authentication and the server speaks plain HTTP by default. Anyone who reaches port 8800 and reads the token has full control of your survey data and your AP tuning history. Keep it on the LAN, or reach it through a VPN or a reverse proxy that terminates TLS and adds its own authentication.

Docker alternative

There is no published container image yet: the compose file in installer/ builds the image locally from the same source. It runs the same server with the same data layout, so two volume mounts are all you need:

cd installer
docker compose up -d --build
docker compose logs -f          # first boot prints the viewer token

The compose file publishes 8800, mounts ./config at /etc/wifisurvey and ./data at /var/lib/wifisurvey, and sets WIFISURVEY_* for host, port and data directory. If config/config.toml does not exist the entrypoint generates one with a fresh viewer_token and pairing_secret, prints the viewer token to the container log, and never replaces it on later starts.

mDNS in containers

avahi inside a bridged container cannot announce on your LAN, so survey.local will not resolve. Either use network_mode: host or simply point clients at http://<SERVER_IP>:8800. Pairing and the API work the same either way.

Upgrade

Upgrades are in place. Take a copy of the database first — migrations are automatic and one-way, so a rollback means restoring the file you saved.

sudo systemctl stop wifi-survey
sudo cp /var/lib/wifisurvey/survey.db /var/lib/wifisurvey/survey.db.bak
cd wifi-survey && git pull
sudo installer/install.sh --upgrade

The script rebuilds the virtual environment, runs pending schema migrations inside a transaction and restarts the unit. A failed migration leaves the database at its previous version and the service stopped, with the error in journalctl -u wifi-survey.

Uninstall

The same script reverses the install. It stops and disables the unit, removes /opt/wifi-survey and the unit file, and asks before deleting configuration and data.

sudo installer/install.sh --uninstall          # keeps /etc and /var/lib after confirmation prompts
sudo installer/install.sh --uninstall --purge  # also deletes config, database and models

With --purge there is nothing left to recover: /opt, /etc/wifisurvey and /var/lib/wifisurvey are all gone, and the wifisurvey user is removed. Copy survey.db somewhere else first if the survey took you an afternoon.
