Privacy

Wi-Fi Survey is a local tool with no account, no cloud and no analytics. This page states exactly what is written to disk, what leaves the machine (nothing, by default), which ports are open, and what remains after you delete data or uninstall.

v0.1~5 min read

The short version: your survey data stays in one directory on your own disk, the server never initiates an outbound connection, and the only listener is the web port you chose. Everything below is detail on that claim.

What is stored

All persistent state lives under /var/lib/wifisurvey, with configuration under /etc/wifisurvey. There is no second location, no cache directory outside the database, and no log shipper.

Two details worth knowing. The journal records the client address of whoever used the UI at the time of an error, so a shared home will show several addresses — that is how you tell a session from a stranger on the LAN when something fails. And the stored BSSIDs include networks that are not yours, because a scan reports everything the radio hears; the section on neighbouring networks covers what that means.

No telemetry

There is no analytics, no crash reporting, no usage counter and no phone-home. The server does not check for updates at startup, and the installer does not contact anything after it has fetched its packages. There is no unique installation id, no device fingerprint and no aggregated statistics endpoint.

If an update check is ever added, it will be opt-in, it will fetch a static version file, and it will send nothing but the request itself — the version you are running would be compared locally, not reported. Until such a feature exists in a release, no part of the software makes an outbound request on its own. You can verify the absence of one with ss -tunp on the server while it runs: you should see the listening socket and your own client connections, nothing else.

The documentation site follows the same rule. It is static HTML with one stylesheet and one script, no fonts hosted elsewhere, no CDN and no third-party embed. Search runs in your browser against a JSON file served from the same directory.

Network listeners

The server binds 0.0.0.0:8800 so that phones and laptops on the LAN can reach it. That is the only socket it opens. There is no separate metrics port, no database listener exposed and no mDNS responder beyond the avahi advertisement for survey.local.

Apart from the login and setup endpoints, every API call requires Authorization: Bearer <YOUR TOKEN>. The exceptions are /healthz, which returns a small status object and no survey data, /api/v1/auth/* and /api/v1/setup/*, which have to be reachable before you have a session, and the pairing endpoints themselves. A node's token only permits posting readings and scans for that node; it cannot read surveys or change configuration.

No TLS by default

Traffic is plain HTTP, including the bearer token. Anyone who can capture packets on your LAN can read the token and replay it. Treat the LAN as the security boundary, keep the port closed at the router, and put a reverse proxy with TLS in front if you need to cross a network you do not control.

UniFi integration

The integration uses a read-only account that you create on your own controller. Controller polling is planned: in v0.1 the wizard stores the URL, site, username and password file, and makes no outbound connection. When it lands it will read the AP list, radio configuration and client associations; it will never write, never change a channel and never reboot anything. The session will be held in memory for the lifetime of the process, not written to disk.

Those credentials go to your controller and nowhere else. They are not sent to the vendor, not included in a support bundle, and not logged. Client MAC addresses are stored as observed, because correlating a device across APs is the whole point of the fingerprinting view; they are never uploaded, and they disappear when the survey is deleted. If you would rather not store MAC addresses at all, leave the integration off — manual AP placement covers everything the heatmap needs.

Browser storage

The web UI keeps your API token in localStorage under a single key. There are no cookies, no session store on the server and no third-party requests: the interface loads only files from the same origin. Clearing site data logs you out and removes the token from that browser.

Because the token is in localStorage, any script running on that origin could read it. That is one more reason the app ships no third-party script and why the deployment sets a content security policy that forbids inline and remote scripts. If you paste the token into a different browser profile, it stays there until you clear it.

Deleting your data

Deletion has three levels, and each one is deliberate about scope:

  • Delete a survey — planned: removes its readings, positions, heatmap cache and the AP placements attached to it. The model file stays until you delete it separately.
  • Revoke a node — kills the token immediately. Existing readings remain, still attributed to that node id.
  • Uninstall with --purge — removes the package, the unit file, /etc/wifisurvey and /var/lib/wifisurvey, including the database, models and token.

After an uninstall with purge, nothing remains on the machine. The only copies that can exist are the ones you made yourself: a database file copied to a NAS, a CSV export in a downloads folder, a support bundle in /tmp. Those are outside the tool's reach and outside its responsibility.

No encryption at rest

The database and models are protected by file permissions and nothing else. Anyone with root, or with physical access to the disk, can read every reading and the UniFi credentials in config.toml. Full-disk encryption is your job — enable it at install time, because retrofitting it to a running system is a copy-and-reinstall exercise.

Neighbouring networks

A Wi-Fi scan reports every BSSID the radio can hear, which on a typical street includes a dozen networks that are not yours. Those rows are stored as part of the survey because excluding them would distort the channel-occupancy view and the interference estimate. They are local data like everything else, and they are never transmitted anywhere.

If you want them out, filter at collection time rather than afterwards. --bssid-filter accepts a list of BSSIDs or SSIDs to drop, so points are stored clean from the start and exports do not carry your neighbours' identifiers. Filtering after the fact leaves the original rows in the database until you delete the survey.

Guest and children's networks deserve the same thought. Their BSSIDs are visible to any scanner, including a phone belonging to someone in the house, and a survey will record them like any other radio. That is a property of Wi-Fi, not of this tool: the fix is the filter above, not a setting that hides a network from passive scanning.
