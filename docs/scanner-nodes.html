Scanner nodes

A node is anything that can scan Wi-Fi and post JSON. The server does not care whether that is a laptop on a charger, a phone in your pocket or a microcontroller taped to a wall — they all speak the same reading schema. What differs is which bands they can see and how much you should trust the number.

v0.1~10 min read

Pairing a node

A node cannot post until it holds a node token. Pairing exchanges a short, single-use code for it, so you never type the server token into a device you might lose.

  1. Print a code on the server

    Run sudo -u wifisurvey -H /opt/wifi-survey/venv/bin/wifi-survey pair, or use the pairing screen in the UI. The server prints a six-digit code. It is valid for ten minutes, once.

  2. Give the node a name

    Use the room or the device — laptop-hall, phone-bedroom, esp32-attic. It is what you will read in the survey list later.

  3. Claim the code

    The agent calls POST /api/v1/pair with code, node_id and node_type. An expired or already-used code is rejected; print a new one. /api/v1/pair/claim is an alias for older agents, not a separate flow.

  4. Store the node token

    The response holds a token for that node only. It can post readings; it cannot read surveys, change AP settings or claim another code.

  5. Confirm the heartbeat

    The node appears under Nodes after its first successful post. A paired node that never posts shows as idle: check the server URL and the clock.

Clocks matter

Readings carry an ISO 8601 UTC timestamp from the node, not the server. A node whose clock is minutes off produces points that sort oddly in the timeline. Enable NTP on laptops and phones; on ESP32 call configTime first.

The reading schema

One POST is one sample at one position: a node identifier, a UTC timestamp, a position on a floor, and an array of per-BSSID observations.

POST /api/v1/readings
Authorization: Bearer <NODE_TOKEN>
Content-Type: application/json

{
  "node_id": "laptop-hall",
  "ts": "2026-02-14T19:42:07Z",
  "position": { "x": 4.25, "y": 2.80, "floor": 0 },
  "samples": [
    { "bssid": "bssid-one", "ssid": "example-net", "band": "5",
      "channel": 36, "freq_mhz": 5180, "rssi": -58 },
    { "bssid": "bssid-two", "ssid": "example-net", "band": "2.4",
      "channel": 6, "freq_mhz": 2437, "rssi": -67 }
  ]
}
FieldTypeRequiredNotes
node_idstringyesMust match the node that owns the token; a mismatch is rejected.
tsstringyesISO 8601 in UTC, with a trailing Z. Local time without an offset is rejected.
position.xnumberyesMetres from the floor origin, along the first axis.
position.ynumberyesMetres from the floor origin, along the second axis.
position.floorintegeryesFloor index as imported: 0 is the lowest floor in the model.
samplesarrayyesAt least one entry. A sample with no BSSIDs is discarded.
samples[].bssidstringyesLowercase, colon-separated. This is the identity used for interpolation and fingerprints.
samples[].ssidstringnoDisplay only. Empty for hidden networks.
samples[].bandstringyes"2.4", "5" or "6". Used to pick the path loss constant.
samples[].channelintegeryesPrimary channel number.
samples[].freq_mhzintegeryesCentre frequency; cross-checked against the channel.
samples[].rssiintegeryesdBm, negative. Values above −10 or below −100 are clamped.

Unknown fields are ignored, so an agent can add diagnostics without breaking ingest. Missing required fields return a validation error naming the path.

Linux agent

The Linux agent is the reference implementation: one stdlib-only Python file, no package, no virtual environment. agent-linux/install.sh copies it to ~/.local/bin, pairs it and optionally installs a systemd user unit — no root and no daemon.

git clone https://github.com/ImVexi/wifi-survey.git
cd wifi-survey

# pair and start scanning
./agent-linux/install.sh --server http://survey.local:8800 \
  --pair-code 123456 --node-id laptop-hall --interval 10

Run the file directly if you prefer: wifi_agent.py --server-url URL --pair-code CODE --node-id NAME --scan-interval 10. The token returned by pairing is saved in ~/.config/wifi-survey/agent.json with mode 0600; --pair-only stops after saving. While running, the agent serves a small status page on http://127.0.0.1:8790/ (plus /status.json and /healthz) showing the last scan, the outbox depth and the last post result.

Under the hood it shells out to nmcli for every sample:

nmcli --terse --fields BSSID,SSID,CHAN,FREQ,SIGNAL dev wifi list

SIGNAL is not dBm. NetworkManager reports 0–100 %, and the agent converts it:

dBm ≈ −100 + 0.6 × pct, clipped at −40 dBm.

The conversion is coarse: the mapping is only accurate to about ±3 dB. When the adapter exposes real dBm through iw, the agent uses that value instead and only falls back to nmcli percentages.

NetworkManager refuses a rescan within roughly 10 seconds. So with --interval 15 you get a fresh scan every sample; intervals below 10 seconds silently reuse the cached list.

Android via Termux

A phone is the most convenient node: you already carry it, and Termux:API gives raw scan results without root.

pkg install termux-api python
termux-wifi-scaninfo          # JSON array of visible BSSIDs

# pair with a code from the server, then sample every 30 s
./termux_agent.sh --server http://survey.local:8800 \
  --pair-code 123456 --node-id phone-kitchen --position 4.2,2.1,0

You need the Termux:API app from the same source as Termux, and location permission granted to it — without it the scan list comes back empty instead of erroring. --position is how v0.1 records where the phone was standing: there is no tap-to-place survey screen yet.

The real constraint is throttling: recent Android versions return roughly four scans every two minutes. An agent asking every 15 seconds gets the same cached list three times out of four. Fine when you stand still for 30 seconds per point, useless for continuous monitoring.

Known limitation

There is no Windows or macOS agent yet — Windows can use the web UI but cannot scan. There is no iOS agent at all, since iOS does not expose scan results to apps. The ESP32 cannot see 5 GHz, so a 5 GHz-only network is invisible to it.

ESP32

An ESP32 makes a cheap fixed node: it sits in one place, scans every interval and reports on 2.4 GHz only. The sketch needs WiFi.h, HTTPClient.h, Preferences.h and about 120 lines.

The outline: on first boot it starts a soft AP with a captive portal asking for Wi-Fi SSID, password, server URL and node token, stores them in NVS through Preferences, then reboots into station mode. The loop is: scan, build the JSON, post, wait.

#include <WiFi.h>
#include <HTTPClient.h>
#include <Preferences.h>

void postReading(const String &body) {
  HTTPClient http;
  http.begin(serverUrl + "/api/v1/readings");
  http.addHeader("Content-Type", "application/json");
  http.addHeader("Authorization", "Bearer " + nodeToken);
  int code = http.POST(body);
  Serial.printf("POST %d\n", code);
  http.end();
}

Two details matter more than the code. The radio reports RSSI directly, with no percentage conversion, so readings are the most consistent of the three — about ±2 dB. And it cannot see 5 GHz: a 5 GHz-only network is invisible, a mixed one appears only via its 2.4 GHz BSSID.

The captive portal is the weakest part: an ESP32 has no clock until it syncs, so call configTime after connecting and refuse to post until the time is real — otherwise every reading says 1970.

Choosing a node

Most people need two: a laptop for the main survey, and one fixed node for a floor that is awkward to walk twice.

  • Use a Linux laptop when you want the whole picture, including 5 GHz, and can walk with it. The only node that produces a multi-band survey in one pass.
  • Use Android when you want to survey without a laptop, or want points at phone height and in a hand — closer to how clients are actually used.
  • Use an ESP32 when the node must stay put: a fixed monitoring point, an outbuilding, a shed. Accept that it sees only 2.4 GHz.

Two rules: do not mix node types within one run — a throttling phone biases the average — and keep node names stable, since the name is what ties readings to a device afterwards.

If you must mix node types, take five points in the same spot with each and compare. A constant offset is normal; a wandering one usually means a node is throttling.

Once a node posts reliably, the next chapter is the walking itself: point counts, spacing and marking positions — see Running a survey. For post failures start with Troubleshooting, and for the numbers themselves see accuracy expectations.
