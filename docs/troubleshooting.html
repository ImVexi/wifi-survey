Troubleshooting

Almost every problem lands in one of three buckets: a node that cannot reach the server, a server that cannot bind its port, or data that is older than the screen you are reading. This chapter works symptom first — find the row that matches what you see, run the check, apply the fix, then test again.

v0.1~10 min read

v0.1 has no doctor or support-bundle command

This chapter assumes the finished tool in a few places. In v0.1 use systemctl status, journalctl and wifi-survey status, and read the config with wifi-survey show-config. wifi-survey doctor, wifi-survey support-bundle and the in-UI factory reset are planned.

Start with the service, not with the browser. Three commands answer "is it running", "what did it last complain about" and "is the configuration coherent":

systemctl status wifi-survey --no-pager
journalctl -u wifi-survey -n 50 --no-pager
sudo -u wifisurvey -H /opt/wifi-survey/venv/bin/wifi-survey status

One change at a time

Each fix below is independent. Apply one, re-test, then move on. If you change three things at once and the symptom disappears, you will not know which one mattered when it returns a month later.

A node shows as offline

A node is offline when the server has not accepted a reading from it inside the expected window. That is a different failure from "the node was never paired", and the two look similar in the UI: both leave the node greyed out in the scanner list. Open the node's detail panel first. If it has a last-seen timestamp, the pairing worked and something broke afterwards. If the panel has no timestamp at all, go straight to the pairing steps at the end of this section.

Node tokens are not the dashboard token. The [security] viewer_token in /etc/wifisurvey/config.toml belongs to the human using the UI; every node gets its own token when it claims a pairing code, and either side can revoke it. Pasting the dashboard token into an agent is the single most common cause of a 401 in the logs.

CheckHow to confirmWhat it usually means
Token revokedNode page shows no last-seen time; the journal has 401 for that node idThe server no longer accepts the node's token. Re-pair the node.
Clock skewCompare timedatectl on the node and the serverReadings stamped more than 60 s away from server time are rejected, so a node with a dead NTP client keeps failing without an obvious error on the device.
mDNS does not resolvegetent hosts survey.local on the nodeAvahi is not running, or the node is on a VLAN where multicast does not reach the server. Use the IP address instead.
Node on a guest VLANCompare the node's subnet with the server'sGuest networks usually block client-to-LAN traffic. Move the node to the main network.
Wrong host or portcurl from the node itselfThe agent is pointed at an address that does not answer, or at port 8800 on a machine where the service is not running.

Test the path from the node, not from your laptop. /healthz needs no token and proves reachability; the second call proves the node token is accepted (a 422 means auth passed and only the empty body was rejected):

curl -sS http://survey.local:8800/healthz

curl -sS -o /dev/null -w '%{http_code}\n' \
  -H 'Authorization: Bearer <NODE_TOKEN>' -H 'Content-Type: application/json' \
  -d '{}' http://survey.local:8800/api/v1/readings
ResultRead it asNext step

To re-pair, revoke the node in the dashboard, generate a new six-digit single-use code, and claim it from the agent within 10 minutes. The claim is a single POST to /api/v1/pair; the code is consumed on first use, so a second device cannot reuse it. If the code expires you will get a plain rejection rather than a partial pairing, and you can simply generate another.

Port 8800 is already in use

The service exits at startup with an address-in-use error, and the unit goes into a restart loop. Find out who owns the port before you change anything:

ss -ltnp | grep 8800

Three outcomes matter. If the process is another wifi-survey instance, you have two units enabled — usually an older manual run plus the systemd unit — and should stop the manual one. If the process is docker-proxy, a container is publishing 8800 and you should move one of the two. If it is an unrelated service, change the Wi-Fi Survey port instead of fighting over it.

You can override the port for a single run with --port, or set it permanently in /etc/wifisurvey/config.toml:

[server]
host = "0.0.0.0"
port = 8788

Restart after editing and confirm the new listener, then update anything that hard-coded the old port — the mDNS advertisement, bookmarks, agent configuration and your firewall rule:

sudo systemctl restart wifi-survey
ss -ltnp | grep 8788

The UI and the API always share one origin, so a port change moves both. Nothing else in the configuration refers to the port by number, but clients do.

The dashboard is unreachable from another device

If curl http://survey.local:8800 works on the server and the same request times out from your laptop, the service is fine and something between the two is dropping packets. Allow the port on the host firewall:

sudo ufw allow 8800/tcp
# or, on Fedora/RHEL family
sudo firewall-cmd --add-port=8800/tcp --permanent
sudo firewall-cmd --reload

Docker bypasses ufw

Ports published with -p 8800:8800 are written straight into the nat table, so ufw rules do not filter them. If you run the container, bind the publish to one interface (-p <SERVER_IP>:8800:8800) or manage the rules in the Docker chain. Checking ufw status alone will tell you the port is blocked while it is in fact wide open.

On a flat home LAN the remaining suspects are client isolation on the access point (often on by default for guest SSIDs) and a router that treats wireless clients as a separate zone. Both are configuration on the network gear, not on the survey server.

Scans are not fresh

"Not fresh" means the numbers on screen do not reflect the room right now. Scan freshness has four usual causes, and only one of them is a fault.

SymptomCauseFix
Two taps seconds apart return identical RSSINetworkManager enforces a rescan cooldown of about 10 s on LinuxWait out the cooldown, or accept that the second sample repeats the first scan. The survey cadence is 15 s per point for this reason.
Android readings plateau or repeatThe platform throttles scan results for foreground apps, and some vendors throttle harder with the screen offKeep the screen on, keep the app in the foreground, and take the sample after a short pause rather than immediately after moving.
Everything looks like it did last weekThe heatmap is rendered from stored readings, and the survey has not been extended since the AP configuration changedTake 3–5 fresh points per affected floor, or re-run the survey for that floor.
Signal changed after you moved an APOld points still describe the old layoutNot a bug. Points are historical; re-survey the rooms the change affects.

If the survey predates a channel, power or placement change, the map is a picture of the old network. Nothing recalibrates automatically, because a reading is a measurement with a timestamp, not a prediction. Comparing before and after is a legitimate use: duplicate the survey, re-walk one floor, and view both.

Model import fails

Import errors are specific. Read the message, then match it here before re-exporting anything.

Message or symptomCauseFix
Model loads on its side or is 100× too largeUp-axis and unit metadata are missing or wrongExport as glTF/GLB with metres and Y-up, or set the axis and scale in the import confirm step.
Rejected for sizeThe upload exceeds the 150 MB capDecimate before export. Scan apps usually offer a "medium" or "reduced" quality that lands well under the limit.
Blank or untextured surfacesThe .gltf references .bin or texture files that were not includedExport a single .glb instead; v0.1 uploads one file and does not unpack archives.
"Unsupported file type" for a ZIPArchives are rejected; only .glb, .gltf and .obj are acceptedUnpack the export and upload the mesh file. ZIP support is planned.
Polycam raw scan imports with no floorA raw capture is a mesh in arbitrary space; floor detection needs a room-mode exportRe-export from Polycam in room mode, or place the floor plane manually in the confirm step.

The confirm editor exists so that a bad import stops before it becomes a bad survey. Check three things before you accept: the floor count matches the building, the wall lines sit on real walls rather than on furniture edges, and the scale bar reads a distance you can verify with a tape measure. Fixing a wall there is cheap; fixing it after 120 readings is not.

The heatmap looks wrong

A heatmap is an interpolation between measured points. Most "wrong" maps are under-sampled maps, or maps drawn at the wrong place.

What you seeLikely causeFix
Large smooth blobs that ignore wallsToo few points for the floor areaAdd points until you have 10–15 per floor, spread across rooms rather than clustered in the doorway.
Strong signal in a room that is weak in realityThe AP is placed on the wrong floor in the modelMove the AP marker to the correct floor; the height difference changes every prediction on that floor.
Signal passes through a wall it should notThat wall is labelled as exterior, or was never classifiedOpen the model editor, select the wall, set it to interior with the right material.
Whole map is one flat colourThe floor selector is on a different storey than the one you surveyedCheck the floor picker before anything else — this one is easy to miss.
Map bleeds across rooms and floorsInterpolation radius set too largeReduce the radius so that a point only influences its own room. Kriging needs at least 10 points before it is worth using.

If the map still disagrees with what a device measures, trust the device for the single spot and trust the map for the trend. The model reports its own held-out error, typically 4–7 dB in a house with drywall and a few brick walls, and that error applies to predictions between points, not to the points themselves. Heatmaps covers the difference between IDW and kriging; Propagation model covers what a wall loss actually changes.

Disk is filling up

Readings grow with time, not with the size of the building. A point stores every BSSID visible from that spot, so a dense street with many neighbouring networks costs more per point than an isolated house. A reasonable estimate is 5–10 kB per reading including indexes, which puts a five-floor house at a few megabytes — small, but not zero if you survey weekly for a year.

Two things keep it bounded today: check the size, and reclaim free pages. A per-server retention window is planned.

du -sh /var/lib/wifisurvey
sudo -u wifisurvey sqlite3 /var/lib/wifisurvey/survey.db \
  'PRAGMA wal_checkpoint(TRUNCATE); VACUUM;'

VACUUM rewrites the database file and returns space freed by deleted rows. It needs free disk equal to the database size while it runs, so do not start it on a filesystem with 20 MB left. A per-server retention window is planned; in v0.1 delete old readings deliberately (after an export) with DELETE FROM readings WHERE ts < ..., then vacuum.

Logs and support bundles

The journal is the primary source. Two hundred lines covers a restart plus the failed requests that follow it:

journalctl -u wifi-survey -n 200 --no-pager
journalctl -u wifi-survey --since "1 hour ago"

In v0.1 the boring checks are manual: ls -l /etc/wifisurvey/config.toml (mode 0640), sudo -u wifisurvey test -w /var/lib/wifisurvey, sqlite3 /var/lib/wifisurvey/survey.db 'PRAGMA integrity_check;', systemctl status avahi-daemon and ss -ltnp | grep 8800. A single wifi-survey doctor command that runs all of them is planned.

When you need to hand the problem to someone else, collect the pieces by hand. A support-bundle command is planned; today the short version is:

journalctl -u wifi-survey -n 500 --no-pager > /tmp/wifi-survey.log
sudo sed -E 's/(viewer_token|pairing_secret)[[:space:]]*=.*/\1 = "REDACTED"/' \
  /etc/wifisurvey/config.toml > /tmp/wifi-survey-config.toml

Redact tokens and UniFi credentials before you send either file anywhere. Logs do not contain raw readings, but they do contain node ids and client addresses.

Reset and recovery

Three operations cover most recovery work. They differ in how much they delete, so pick deliberately.

Reset a node token

Revoking a token is immediate and does not touch survey data. Old readings stay attributed to the same node id, so history and fingerprints remain intact. Open the node, choose revoke, then pair again with a fresh six-digit code. Use this when a device is lost, when a token was pasted into the wrong place, or when you are re-flashing an ESP32 and want the old credential dead.

Re-import a model without losing points

Points are stored against coordinates on a floor, not against the mesh, so a model can be replaced while the readings survive. Import the corrected model, align the floor plane to the same origin at the same scale, and confirm. If the new model is rotated or scaled differently, existing points will sit in the wrong place — realign before you accept, and check one known room against the old map. Deleting the survey and starting over is the last resort, not the first.

Factory reset

A factory reset removes the database, imported models, node registrations and the API token, and returns the configuration to defaults. It does not touch the installed binary. Take a copy of /var/lib/wifisurvey first if there is any chance you want the old survey; a reset is not undoable.

ItemDeleted by factory resetKept

Imported models and wall editsYes—

No remote support path

There is no crash reporting, no telemetry and no automatic upload of logs or bundles. A support bundle only leaves the machine if you copy it out yourself. That also means nobody is watching your instance for failures: if the UI is wrong, the journal is the only record, so collect it before you restart the service.
