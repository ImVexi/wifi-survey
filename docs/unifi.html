UniFi integration

Wi-Fi Survey can read your access point inventory straight from a UniFi controller so you do not have to type in models, channels and transmit power. It is optional, it is read-only by default, and the whole feature works without it.

v0.1~5 min read

Planned — not in v0.1: polling

The setup wizard can store a controller URL, site name and read-only credentials (POST /api/v1/setup/unifi, password in unifi.password under the data directory, mode 0600), and /api/v1/unifi/status reports what is configured. Nothing is polled yet: no AP list, channels or client data are imported, and the server makes no outbound call to the controller. Everything below describes the integration that will sit on top of those stored settings.

Create a local read-only account

Do not reuse your administrator account. Make a dedicated account with the smallest set of rights that still lets it list devices, and treat the password as a credential for this tool alone.

  1. Settings → Admins & Users → Invite Admin.
  2. Choose "Local Access Only". A cloud-linked account will not authenticate against the local API the way this integration needs.
  3. Assign the Read Only role and leave every site-administration right off. Reading is all the integration does.
  4. Set a long, unique password. It is stored in a configuration file on your server, so it should not be a password you use elsewhere.
  5. Do not enable two-factor authentication on this account. 2FA breaks scripted login: the API expects a username and password and has nowhere to put a one-time code, so the poll fails on every attempt.

If your controller version supports API keys, use one instead of a password and skip the 2FA problem entirely — the key is scoped to the account and can be revoked without changing anything else. Where keys are not available, the local account with 2FA disabled is the only workable option, which is why it is worth giving that account no rights beyond reading.

Point the tool at your controller

The URL depends on what you are running. A self-hosted software controller on a Linux host normally answers on port 8443:

[unifi]
host = "https://<CONTROLLER>:8443"
site = "default"
username = "wifi-survey"
password = "..."
insecure = false

A UniFi OS console — a Dream Machine, Cloud Key or similar — serves the network application behind a prefix instead, on the standard HTTPS port, so the API path becomes /proxy/network/api/... rather than /api/.... The tool detects the prefix from the controller's response, but if you are constructing URLs by hand, that difference is the usual reason a request returns HTML instead of JSON. The site name is usually default; if you renamed your site, use the name shown in the controller's site switcher.

Most controllers present a self-signed certificate. There is a --insecure flag that disables certificate verification and lets the connection proceed, and it is genuinely risky: with verification off, anything that can intercept traffic between the server and the controller can present its own certificate, collect the login and then use the session. The better fix is to import the controller's certificate into the server's trust store and leave verification on. Use --insecure on a trusted LAN when you have no other option, not as a default.

Once connected, the integration polls every 60 seconds. If a poll fails — controller rebooting, network hiccup, expired session — it backs off and retries, and marks the integration stale in the UI rather than showing the last good values as if they were current.

What it calls

PathMethodReturnsWhy it is read
/api/auth/loginPOSTSession cookieAuthenticates the read-only account; on UniFi OS consoles it sits behind /proxy/network
/api/s/<site>/stat/deviceGETAP inventoryModels, channels, channel widths and transmit power for every AP
/api/s/<site>/stat/staGETClient listWhich client is on which AP, and its RSSI — used for sticky-client views
/api/s/<site>/rest/wlanconfGETWireless network configSSID names, bands and security mode; passwords are not returned
/api/s/<site>/stat/report/dailyGETDaily historyHistorical client counts, so a coverage problem can be matched to when it happens

Only these five are used. The session established by the login call is kept in memory for the life of the poller and is never written to disk.

What is read, and what never is

The integration reads inventory and counters: device models, firmware versions, channels, widths, transmit power, client associations, RSSI values and SSID names. That is enough to fill in the access point list, draw the client distribution and feed the tuning rules.

It never reads client traffic, never touches deep packet inspection data, never requests WPA passphrases or PSKs, and never writes anything. There is no code path that changes a channel, a power level or an SSID through the controller API — tuning changes, when you enable them, go through the same read-write session type but are a separate, explicitly enabled feature with their own guardrails.

If you would rather not hand over credentials at all, skip to manual mode. Nothing except the live client counts depends on the controller.

Where the credentials live

Controller credentials are stored in /etc/wifisurvey/config.toml with mode 0600, owned by the service user. Nothing in that file is served over HTTP, and the API never echoes a password back. The session cookie lives in the process's memory only, so a restart means a fresh login rather than a replay of an old session.

No cloud connector is needed or used. The UniFi cloud is not contacted, the controller is reached directly on your LAN, and the integration works with a purely local account — which is the other reason to create one. Nothing about the controller leaves your network.

Manual mode

Manual mode is the default and it is not a degraded experience. You add each access point yourself: name, model, band, channel, width and transmit power. The tool uses that to place the AP on the plan, run the propagation model and evaluate tuning rules.

What you lose is only what requires live data from the controller: current client associations, per-client RSSI, and historical client counts. Everything else — heatmaps, calibration, held-out error, model previews and most of the recommendations — works the same. If you check your controller's UI once a month and type in any changes, manual mode stays accurate enough for survey work.

Limits

UniFi OS and the older self-hosted controller differ in URL layout, login response shape and where the network application is mounted. Both are supported, but a mixed environment may need the prefix set explicitly. Hosted and remote controllers are not supported at all: the integration expects to reach the controller directly on the LAN, and it will not tunnel through a cloud relay.

Not supported

Hosted or remote UniFi controllers, Omada and other controller platforms, and any write operation outside the tuning feature. UniFi firmware changes the private API without notice; when that happens the integration breaks until the parser is updated, and manual mode is the workaround. Treat this as a convenience layer, not a dependency.
